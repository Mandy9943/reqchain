# reqchain — design spec

Date: 2026-09-16
Status: approved for planning
Name: `reqchain` (provisional)

## 1. Purpose

A deliberately small desktop HTTP client for Ubuntu 24.04 / GNOME, built around the one
problem generic clients handle badly: **authentication that depends on a previous
request**. A business endpoint needs `Authorization: Bearer <token>`; the token comes
from calling `POST /token` first. The app must do that automatically, cache the token
with its TTL, refresh it on expiry or 401, and let the user inspect the auth request and
its response instead of hiding it.

Secondary purpose, equally binding on the design: the on-disk format is readable,
documented and validatable, so an AI agent (Claude Code) can write request files
directly and have them appear, runnable, in the app.

## 2. Non-goals

No accounts or login, no cloud sync, no collaboration, no mocks, no test suites, no
autogenerated documentation, no performance charts. If any of these arrive "for free"
with a dependency, they stay out of the UI.

## 3. Stack decisions

| Layer | Choice |
|---|---|
| Core | Rust crate `reqchain-core` — reqwest, serde, notify, jsonpath, md5/sha1/sha256 |
| CLI | Rust binary `reqchain` — `list`, `run`, `validate` |
| UI | Tauri 2 + Svelte 5 + CodeMirror 6 |
| Package | `.deb` with `.desktop` entry and icon |

Rationale (3 lines, as requested): Tauri gives a ~15 MB binary with sub-second cold
start and a trivial `.deb`, which is what "open it, fire one request, close it" needs;
Electron would cost ~150 MB and 1–2 s of startup for the same UI; GTK4 would be lighter
still but its text widgets make a JSON body editor and a searchable response viewer much
more work to build and to maintain later.

What each loses: **Tauri** — a Rust toolchain plus `libwebkit2gtk-4.1-dev` must be
installed once, and maintenance means touching two languages. **Electron** — startup and
size, the two things explicitly prioritised. **GTK4** — editor and response-viewer
quality, and (with Rust) the highest build effort of the three.

All logic lives in `reqchain-core`. The CLI and the Tauri backend are thin shells over
it, so every rule below is testable headless.

## 4. Storage layout

```
~/.config/reqchain/
├── workspace/                          # git-versionable, never contains secrets
│   ├── apis/
│   │   └── example-gateway-test.json    # one API: config + environments + endpoints
│   └── .gitignore
├── secrets.json                        # mode 0600, source of {{secret:NAME}}
├── cache/tokens.json                   # mode 0600, CLI token cache
└── history/<api>/<endpoint>.jsonl      # last N executions per endpoint
```

The workspace directory is overridable with `REQCHAIN_DIR`.

**One file per API, not per endpoint.** An auth chain never crosses API boundaries, so a
whole chain — the token endpoint, the business endpoint that derives from it, and the
shared credentials — is reviewable in a single diff and writable by an agent in a single
file write. APIs hold few enough endpoints that file size is not a concern.

Git-friendliness is enforced, not hoped for: keys are emitted in a fixed order defined by
the struct field order, indentation is 2 spaces, a trailing newline is always written, and
no timestamps, ids or run counters are ever persisted into workspace files. History,
cache and secrets live outside `workspace/` for the same reason.

## 5. File format

`schemaVersion: 1` at the top of every API file. Full grammar and examples go in
`SPEC.md`; this section fixes the semantics.

### 5.1 API

`id`, `name`, `baseUrl`, `variables`, `environments[]` (each with `name` and
`variables`), `auth` (inherited default), `endpoints[]`.

### 5.2 Endpoint

`id`, `name`, `method` (GET, POST, PUT, PATCH, DELETE, HEAD, OPTIONS), `path` relative to
the API `baseUrl`, `headers`, `query`, `body`, `variables`, and
`auth: "inherit" | "none" | <auth object>`.

Bodies: `json`, `form` (urlencoded), `multipart`, `text`, `xml`, `binary` (file path).

### 5.3 Variables

`{{var}}` interpolates into url, path, headers, query and body. Resolution is
**most-specific-first: endpoint → active environment → API**. An unresolved variable is
an error before the request is sent, naming the variable and where it was referenced.

`{{secret:NAME}}` resolves only from `~/.config/reqchain/secrets.json`. Secret values are
never written to workspace files, never to history, and are masked in the effective-request
view and in `copy as curl` unless the user explicitly reveals them. GNOME keyring support
is deferred to a later phase and noted as such in `SPEC.md`.

### 5.4 Auth types

- `none`
- `basic` — `username`, `password`
- `bearer` — `token` (static)
- `header` — N name/value pairs
- `computed` — a header whose value is an expression (§6)
- `chained` — the core feature (§7)

## 6. Expression language

Closed, hand-written parser. No JavaScript, no `eval`. Grammar:

```
expr    := term ( "+" term )*
term    := funcall | string | varref
funcall := name "(" [ expr ( "," expr )* ] ")"
varref  := "{{" name "}}"
```

Functions: `md5`, `sha1`, `sha256`, `base64`, `now(format)`. `now` accepts
`YYYY`, `MM`, `DD`, `HH`, `mm`, `ss` and literal characters; it uses local time.
`+` concatenates strings.

An unknown function is a validation error naming the function and listing the supported
set. Example from the acceptance case: `md5(now("YYYYMMDD") + person_id)`.

## 7. Chained auth

```json
"auth": {
  "type": "chained",
  "source": { "endpoint": "token" },
  "extract": { "from": "body", "jsonPath": "$.access_token" },
  "ttl":     { "from": "body", "jsonPath": "$.expires_in", "unit": "seconds" },
  "inject":  { "into": "header", "name": "Authorization", "template": "Bearer {{value}}" },
  "retryOn": [401, 403]
}
```

- `extract.from`: `body` (with `jsonPath`, `xpath` or `regex`), `header` (with `name`,
  optional `regex`), or `status`.
- `ttl.from`: `body` (a field, with `unit`), `fixed` (with `seconds`), or `absolute`
  (a date field parsed as RFC 3339).
- `inject.into`: `header` (with `name` and `template`), `query` (with `name`), or `body`
  (with a JSON pointer).
- `retryOn`: on these statuses the cached token is invalidated and the chain re-run
  **exactly once**, then the real request is repeated. A second failure is reported as-is.

**Defaults.** If `extract` is omitted it defaults to
`{ "from": "body", "jsonPath": "$.access_token" }`; if `ttl` is omitted it defaults to
`{ "from": "body", "jsonPath": "$.expires_in", "unit": "seconds" }`. These are documented
conveniences for the common OAuth2 `client_credentials` shape, not engine assumptions.
`validate` emits a **warning** whenever a chained auth relies on either default. If the
defaulted path is missing at runtime the error names it explicitly, e.g.
`chained auth: default extract $.access_token not found in response body (keys: token,
expiry) — set auth.extract explicitly`.

**Chaining depth and cycles.** A source endpoint may itself use chained auth. Resolution
is a depth-first walk with a visited set; a cycle is reported as a validation error naming
the full path (`a → b → a`). Maximum depth is 5, exceeded depth is an error.

**Token cache.** Keyed by `api id + hash(resolved auth definition)`, so changing a
credential or an environment invalidates it. The UI holds it in memory; the CLI persists
it to `~/.config/reqchain/cache/tokens.json` (0600) so consecutive `reqchain run` calls
reuse a live token. A token is considered expired 30 s before its nominal TTL.

**Visibility.** The auth request and its response are first-class in the UI: after a run
the response panel offers an "Auth" tab showing the chained request that was executed, its
effective form, status, timing and body. Never a black box.

## 8. Execution and response

Every run records status, elapsed time, response size, response headers, and the
**effective request** — url, headers, query and body with all variables and auth already
resolved (secrets masked). `Copy as curl` emits that same effective request.

Response viewer: pretty-print and search for JSON, XML, HTML and plain text; raw view
always available; binary responses are reported by type and size, not rendered.

History: last N (default 20) executions per endpoint in `history/<api>/<endpoint>.jsonl`,
with a per-API `history.storeBodies: false` switch for sensitive endpoints; request and
response bodies are then omitted while metadata is kept.

## 9. File watching and error handling

The app watches `workspace/` with `notify` (debounced 200 ms) and hot-reloads changed
files without losing UI state: the selected endpoint, the editor's unsaved buffer and the
current response panel survive a reload. If the selected endpoint disappears from disk,
the UI keeps showing it, marked as removed.

An invalid file is surfaced as a readable error in the sidebar — file, line, column and
message — and the app **never rewrites or deletes it**. Other APIs keep working. This is
what makes agent-written files safe to iterate on.

## 10. Agent interface

- `SPEC.md` — short, precise, self-contained description of the file format with complete
  worked examples, written so an agent can generate a valid file with no other context.
- `schema/reqchain-api.schema.json` — published JSON Schema, versioned with
  `schemaVersion`.
- `reqchain validate <file>` — schema plus semantic checks (unknown variables, unknown
  expression functions, chained auth pointing at a missing endpoint, cycles, defaults
  warnings). Errors are actionable: path, what was found, what was expected.
- `reqchain list` — APIs and their endpoints.
- `reqchain run <api> <endpoint> [--env <name>]` — runs the full chain and prints the
  response; exit code reflects transport and validation failure, not HTTP status.

**MCP server: not needed, and not built.** Claude Code already has filesystem and shell
access, so an MCP server would wrap `validate` and `run` in an extra process without
adding a capability. `SPEC.md` + JSON Schema + CLI is a strictly smaller moving part for
the same result. An MCP wrapper only pays off for agents with no shell access; recorded
as a possible phase 2, deliberately not implemented now.

## 11. UI

Single window: sidebar (APIs → endpoints, with search), request panel (method, path,
headers, query, body, auth), response panel (status/time/size, body, headers, effective
request, auth tab). Environment selector per API in the sidebar header.

Shortcuts: `Ctrl+Enter` send, `Ctrl+K` endpoint search. Cold start target under one
second.

## 12. Packaging

`.deb` shipping the binary, a `.desktop` entry and an icon in the standard hicolor path,
so the app appears in the GNOME overview and can be pinned with "Add to favorites".
AppImage is not produced: for a single Ubuntu 24.04 machine it adds a build target and
requires placing the `.desktop` and icon by hand for the dock to work, which is the one
thing the `.deb` does automatically. The trade-off recorded here is that the `.deb` is
tied to this Ubuntu release's library versions and has no self-update.

An install script handles the one-time prerequisites (`rustup`, `libwebkit2gtk-4.1-dev`,
`build-essential`) and is documented in the README.

## 13. Testing

Critical paths, all headless against a local mock server (`wiremock`):

1. **Variable resolution** — precedence endpoint → environment → API, interpolation in
   url/headers/query/body, unresolved variable error, `{{secret:}}` resolution and masking.
2. **Expression language** — each function, concatenation, `now` formats, unknown function
   error, the `md5(now("YYYYMMDD") + person_id)` case.
3. **Auth chain** — chained run without the source endpoint having been run manually,
   extraction by jsonPath / header / regex, injection as header / query / body, multi-level
   chaining, cycle detection, depth limit.
4. **Token cache and refresh** — cache hit, TTL expiry, 30 s skew, refresh-on-401 exactly
   once, no infinite retry on repeated 401, cache invalidation when credentials change.
5. **Invalid files** — malformed JSON, wrong `schemaVersion`, missing required fields,
   chained auth pointing at a missing endpoint; each produces a readable error, leaves the
   file untouched, and does not affect other APIs.

## 14. Acceptance criteria

**Case 1 — chained auth.** API "Example Gateway (test)",
`baseUrl = https://api-manager.example.com`. Endpoint `token`: `POST /token`,
basic auth with username and password as secrets, form-urlencoded body
`grant_type=client_credentials`. Endpoint `repairQuery`: `POST
/repairs/1.0`, chained auth on `token`, extracting `$.access_token`, injected
as `Authorization: Bearer {{value}}`, TTL from `$.expires_in`, JSON body
`{"RepairQuery_In":{"PersonId":"{{person_id}}"}}` with `person_id` as an
environment variable. Pressing Send on `repairQuery` without having run `token`
must work, and an expired token must be refreshed without user action.

**Case 2 — computed header.** API `https://api.example.com`, `GET /library/user`
with headers `user: {{person_id}}`, `hash: md5(now("YYYYMMDD") + person_id)` and
`token: {{secret:API_TOKEN}}`.

Both cases are verified automatically against the mock server. The real API files are
shipped ready to run so they can be executed against the live test gateway by hand, with
credentials supplied locally in `secrets.json`.

## 15. Build order

1. `reqchain-core` + CLI + `SPEC.md` + JSON Schema + the §13 tests — fully verifiable
   without a GUI.
2. Tauri UI — sidebar, request and response panels, environment selector, hot reload,
   shortcuts, copy as curl, history.
3. Packaging — `.deb`, `.desktop`, icon, install script, README.

## 16. Amendments after phase 2

**§11, request panel. WITHDRAWN — see §17.** Phase 2 replaced the enumerated fields with
a single CodeMirror editor over the API's whole JSON file, and this section previously
ratified that. The ratification was wrong and is withdrawn: §11 said fields, and §11 was
right. The stated justification — that a field editor would need a second serializer
capable of disagreeing with `Api::to_json_string` — does not survive examination. A form
edits the typed model and saves through the same `save_api` command and the same
serializer; and because the model is closed (`deny_unknown_fields`, a single
`schemaVersion`), a form cannot silently drop a field it does not know about, because no
such field can exist. The real defect was never technical: the JSON file is the
interchange format an agent writes, not the interface a person operates.

**§5.3, revealing secrets** and **§8, copy as curl.** Both are recorded as known gaps in
`SPEC.md` under "Known gaps in the desktop app". A reveal path is phase 3 work; it opens a
hole in a masking boundary and deserves its own design, not a line in a fix round.

**§7, preview.** Selecting an endpoint never performs its auth request. `preview_endpoint`
resolves variables and static auth but renders a chained credential as a placeholder
naming its source endpoint. Resolving a chain is a side effect on a real server, and it
must follow from pressing Send — not from clicking around the sidebar.


## 17. Visual editing (phase 2.5)

Phase 2 shipped a window you can run requests from but not build them in: creating an API
or an endpoint meant writing a file outside the app, and the only editing surface was raw
JSON. That fails §11 and it fails the product — a user opening the app cold has no way in.

**The forms are the interface; the JSON is the interchange format.** The request panel
presents the model as fields, and the file is what an agent reads and writes.

### 17.1 What is editable

- **API**: name, `baseUrl`, variables, environments (add, remove, rename, and per-environment
  variables), and the inherited `auth`.
- **Endpoint**: method, path, headers and query as key/value rows, body (a type selector
  with the editor that type needs — JSON, form, multipart, text, XML, binary), and `auth`.
- **Auth**: a type selector with the fields that type requires. For `chained` this is a
  guided builder, not a JSON blob: the source endpoint comes from a list of the API's own
  endpoints, and extract, TTL, injection and `retryOn` are each presented as the choice
  they are. This is the app's defining feature and it is the one that most needs not to be
  hand-written.
- **Structure**: create and delete APIs and endpoints.

### 17.2 The JSON tab

Every API keeps a secondary `JSON` tab holding the phase-2 editor, so the file an agent
wrote can be read and hand-edited without leaving the window. Both surfaces edit one
buffer and save through `save_api`; neither gets its own serializer.

### 17.3 Secrets

A secrets screen manages `{{secret:NAME}}` entries — create, replace, delete, and **read**
— so the app can be configured and debugged without a terminal.

Values are readable. An earlier draft of this section made the screen write-only; that was
wrong. `secrets.json` is a plaintext file in the user's own home directory that they can
open in any editor, so refusing to show a value inside the app protects nothing and
removes the answer to the question the screen exists for: a request failed with 401 — is
the credential I stored the one I think it is?

The risk worth designing against is not the disk, it is the screen: a shared display, a
screenshot, someone walking past. So:

- Every value renders masked by default.
- Revealing is explicit, one entry at a time, and never sticky: a revealed value re-masks
  when the screen is left.
- The reveal exists ONLY on the secrets screen. Everywhere a credential could otherwise
  end up — the effective request, the auth trace, the response, run history on disk, error
  text — stays masked unconditionally. Those are the paths a phase-2 adversarial review
  closed one at a time, and this section does not reopen any of them.

The file keeps mode 0600 and stays outside `workspace/`, exactly as §4 requires.

This also supersedes §5.3's blanket "masked unless the user explicitly reveals them" being
listed as unbuilt: the reveal now exists for stored secrets. It is still NOT built for the
`copy as curl` export, which continues to emit `***` — that is a separate surface (text
leaving the app, headed for a clipboard and probably a terminal history) and it gets its
own decision rather than inheriting this one.

### 17.4 What does not change

Storage, the file format, `schemaVersion`, the masking boundary, the chained-auth engine
and the CLI are untouched. This phase adds an editing surface over the model that already
exists; if it requires a change to `reqchain-core`'s semantics, that is a sign the form is
wrong, not the core.
